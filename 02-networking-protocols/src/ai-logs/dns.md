# DNS — анализ и дополнительные сведения

## 1. Анализ полей DNS-пакета и кодирование имени

В лабораторной работе DNS-запрос выполняется с R2 (`10.10.10.2`) на DNS-сервер R1 (`10.10.10.1`).

По захваченному в Wireshark пакету:

- Протокол: DNS
- IP-источник: `10.10.10.2`
- IP-назначение: `10.10.10.1`
- UDP-порт источника: `54315`
- UDP-порт назначения: `53`
- DNS-сообщение: запрос (Query)
- Запрашиваемое имя: `my.site`
- Type: `A`
- Class: `IN`

Основные поля DNS-пакета:

- **Transaction ID** — идентификатор DNS-запроса. Он позволяет сопоставить запрос с соответствующим ответом.
- **Flags** — флаги DNS-сообщения. Они определяют, является ли пакет запросом или ответом, а также содержат дополнительные признаки, например запрос рекурсии.
- **Questions** — количество вопросов в DNS-запросе.
- **Answers** — количество записей-ответов. В самом запросе обычно значение равно `0`, а в ответе оно содержит количество возвращённых ресурсных записей.
- **Name** — доменное имя, для которого выполняется запрос.
- **Type** — тип запрашиваемой записи. В нашей лабораторной работе используется `A`, то есть IPv4-адрес.
- **Class** — класс DNS-записи. `IN` означает Internet.

### Кодирование имени `my.site`

В DNS доменное имя передаётся не одной строкой. Оно разбивается на отдельные метки (labels), перед каждой меткой указывается её длина.

Имя:

`my.site`

разбивается на:

- `my` — 2 символа;
- `site` — 4 символа.

В представлении DNS это выглядит концептуально так:

`02 my 04 site 00`

где:

- `02` — длина метки `my`;
- `my` — сама метка;
- `04` — длина метки `site`;
- `site` — сама метка;
- `00` — нулевой октет, обозначающий конец доменного имени.

Таким образом, DNS использует последовательность меток с указанием их длины, а не хранит имя `my.site` как обычную строку с точкой.

## 2. Краткая иерархия рекурсивного DNS-запроса

Предположим, что DNS-сервер настроен для своей зоны `my.site`, а клиент через этот же сервер запрашивает имя `www.google.com`.

Если на сервере разрешена рекурсия и он может выполнять внешние DNS-запросы, сервер самостоятельно проходит DNS-иерархию:

1. **Корневые DNS-серверы (Root)** — указывают, где находятся серверы зоны `.com`.
2. **TLD-серверы `.com`** — указывают, какие авторитативные DNS-серверы обслуживают домен `google.com`.
3. **Авторитативный DNS-сервер `google.com`** — возвращает информацию о запрошенном имени `www.google.com`.
4. Рекурсивный сервер получает ответ, при необходимости сохраняет его в кэше и возвращает результат клиенту.

Схематично:

`Клиент → рекурсивный DNS-сервер → Root → TLD .com → Authoritative DNS google.com → рекурсивный сервер → Клиент`

Важно, что наличие только зоны `my.site` само по себе не означает, что сервер сможет разрешать внешние домены. Если рекурсия не разрешена или сервер не настроен для внешнего разрешения имён, запрос `www.google.com` он не сможет обработать как рекурсивный и может вернуть ошибку, например `REFUSED` или `SERVFAIL`.

## 3. Три DNS-записи кроме A

### AAAA

**Назначение:** хранит IPv6-адрес хоста.

Пример:

`my.site. IN AAAA 2001:db8::1`

При запросе типа `AAAA` DNS-сервер возвращает IPv6-адрес.

### CNAME

**Назначение:** создаёт псевдоним (alias) для другого доменного имени.

Пример:

`www.my.site. IN CNAME my.site.`

В этом случае `www.my.site` является псевдонимом `my.site`.

### MX

**Назначение:** указывает почтовый сервер, который принимает электронную почту для домена. У MX-записи также есть приоритет: меньшее значение означает более высокий приоритет.

Пример:

`my.site. IN MX 10 mail.my.site.`

В данном случае почта для `my.site` должна доставляться на `mail.my.site` с приоритетом `10`.

## Вывод

В ходе лабораторной работы был выполнен DNS-запрос для `my.site`. В захваченном Wireshark пакете запрос отправляется от R2 (`10.10.10.2`) к DNS-серверу R1 (`10.10.10.1`) по UDP на порт `53`. Для имени `my.site` используется запись типа `A` класса `IN`, предназначенная для получения IPv4-адреса.
