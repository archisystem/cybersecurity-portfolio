# Анализ захвата SSH

## 1. TCP three-way handshake

В захвате Wireshark от R1 (`10.10.40.1`) к R2 (`10.10.40.2`) виден TCP-сеанс к порту 22.

Для первого соединения:

1. **Packet 6 — SYN**
   - Направление: `10.10.40.1 → 10.10.40.2`
   - Порт источника: `23172`
   - Порт назначения: `22`
   - TCP: `SYN`
   - `Seq: 0`
   - `Len: 0`
   - R1 начинает установление TCP-соединения с SSH-сервером R2.

2. **Packet 7 — SYN, ACK**
   - Направление: `10.10.40.2 → 10.10.40.1`
   - TCP-флаги: `SYN, ACK`
   - R2 подтверждает получение SYN и отвечает своим SYN.

3. **Packet 8 — ACK**
   - Направление: `10.10.40.1 → 10.10.40.2`
   - TCP-флаг: `ACK`
   - R1 подтверждает ответ R2.

Таким образом, наблюдается стандартное трёхэтапное установление TCP-соединения: **SYN → SYN-ACK → ACK**.

В захвате также виден второй TCP-сеанс:

- Packet 30: `10.10.40.1 → 10.10.40.2`, `51415 → 22`, `SYN`
- Packet 31: `10.10.40.2 → 10.10.40.1`, `22 → 51415`, `SYN, ACK`
- Packet 32: `10.10.40.1 → 10.10.40.2`, `51415 → 22`, `ACK`

Это связано со вторым подключением к SSH, выполненным после проверки порта через telnet.

### Что означают TCP-флаги

- **SYN** — начало установления TCP-соединения и согласование начального номера последовательности.
- **SYN + ACK** — сервер подтверждает SYN клиента и отправляет свой SYN.
- **ACK** — подтверждение полученного сегмента; после него TCP-соединение считается установленным.

Начальный номер последовательности в отображении выбранного Packet 6 — `Seq: 0`. Это относительная нумерация Wireshark; она удобна для анализа последовательности TCP-пакетов.

## 2. Установление SSH-сеанса

Перед настоящим SSH-подключением была выполнена проверка:

`telnet 10.10.40.2 22`

В захвате/терминале сервер ответил:

`SSH-1.99-Cisco-1.25`

Это показывает, что TCP-порт 22 доступен и на нём работает SSH-сервис Cisco.

После проверки был выполнен настоящий SSH-сеанс:

`ssh -l admin 10.10.40.2`

После ввода пароля появилось приглашение:

`R2#`

Это подтверждает успешную аутентификацию и вход на R2 по SSH. После команды `exit` соединение было закрыто.

В Wireshark после TCP handshake видны пакеты с протоколом **SSH**. В захвате присутствует обмен служебной информацией SSH, после чего содержимое сеанса не представлено как обычный открытый текст команд пользователя.

На R2 перед подключением были созданы RSA-ключи размером **1024 бит**, локальный пользователь `admin`, а для VTY был разрешён вход через локальную учётную запись и `transport input ssh`.

## 3. Роль RSA-ключей

RSA-ключ был создан на R2 командой:

`crypto key generate rsa`

с размером модуля **1024 бит**.

RSA-ключи необходимы SSH-серверу для криптографической идентификации и установления защищённого сеанса. В SSH используются криптографические механизмы для проверки подлинности сервера и согласования защищённого обмена.

При этом сам RSA-ключ не следует ожидать в захвате как открытый текст: сетевой трафик SSH после начальных этапов устанавливает защищённый обмен.

## 4. Telnet и SSH

В этой лабораторной Telnet использовался для проверки доступности TCP-порта 22:

`telnet 10.10.40.2 22`

Важно: это не означает, что R2 начал работать по протоколу Telnet. Клиент Telnet здесь просто открыл TCP-соединение с портом 22, а сервер ответил своим SSH-баннером:

`SSH-1.99-Cisco-1.25`

Основное различие:

- **Telnet** обычно передаёт данные сеанса без криптографического шифрования, поэтому содержимое может быть прочитано при перехвате трафика.
- **SSH** предназначен для защищённого удалённого доступа: после установления TCP-соединения выполняется SSH-обмен и создаётся защищённый криптографический сеанс.

Поэтому при анализе дампа важно отличать проверку `telnet ... 22` от полноценной Telnet-сессии: в данной работе Telnet использовался как способ проверить доступность TCP/22, а удалённый доступ выполнялся именно по SSH.

## 5. Итог

В захвате подтверждены:

- TCP three-way handshake: **SYN → SYN-ACK → ACK**;
- подключение R1 (`10.10.40.1`) к R2 (`10.10.40.2`) на **TCP-порт 22**;
- доступность порта 22 через команду Telnet;
- SSH-баннер `SSH-1.99-Cisco-1.25`;
- успешное SSH-подключение пользователя `admin`;
- наличие SSH-пакетов после установления TCP-соединения;
- второй TCP-сеанс, соответствующий последующему SSH-подключению.

Захват сохранён в файле `ssh.pcap`.
